Каждая задача с новым обязательным сценарием включает его запуск в PR. Владелец общей команды запускает её и локально, и в CI. На переходный период сохраняем рабочие команды для существующих наборов.

### 01. Правила отмены и unit-покрытие

- [x] Команды `test:unit` и `test:unit:cov` работают на Node.js без Docker, сети и запуска приложений. Таблица проверяет решения для неоплаченного, оплаченного, отправленного, доставленного и уже отменённого заказа. При необходимости вынести решение из транзакции, сохранив контракт Orders.
- [x] Для перенесённой и новой прикладной логики обязательны 100% строк, веток, функций и инструкций. Проверить настройку временным добавлением неимпортируемого файла с логикой: CI должен обнаружить пробел. Старые ещё не перенесённые файлы явно учтены, их список может только сокращаться.
- [ ] В PR доступны отчёт покрытия и отдельные замеры времени обычного unit-прогона и прогона с покрытием.

Сбор отчёта и замеры настроены в workflow. Публикацию артефакта проверяем при первом запуске на PR.

### 02. Последняя единица товара на PostgreSQL

- [x] Команда `test:integration` сама поднимает временную PostgreSQL через Testcontainers, применяет миграции Products с выключенной автосинхронизацией схемы и использует изолированные данные. Работает с чистого checkout после установки зависимостей.
- [x] Два разных заказа одновременно запрашивают по одной единице одного товара. Успешен ровно один резерв, отказ вызван нехваткой товара, в БД остаток 0 и одна успешная запись резерва.
- [x] Отсутствие Docker или сбой миграции завершают обязательную проверку ошибкой. Сохраняются логи первого падения, затем временное окружение удаляется. Этот порядок используется и для остальных integration-задач.

### 03. Оформление и повторная отмена через Gateway

- [x] Команда `test:e2e` запускает шесть собранных приложений и их PostgreSQL, MongoDB, Redis и Kafka в отдельном Compose-проекте. Ждёт готовности сервисов. Два прогона могут работать одновременно со своими портами, данными, сетями и томами. После ошибки сохраняются логи и удаляются ресурсы конкретного прогона.
- [x] Подготовить покупателя и товар с остатком 1. Через Gateway положить товар в корзину, оформить заказ, проверить статус `PENDING` и прочитать остаток 0. PayPal для этого пути не требуется.
- [x] Два запроса отмены от владельца возвращают HTTP 200, один ID и статус `CANCELLED`. После каждого запроса каталог показывает остаток 1. Отдельное чтение заказа подтверждает сохранённый статус.

### 04. Отказ резерва доходит до клиента как HTTP 400

- [x] Использовать запуск приложений из задачи 03. Создать управляемое условие, при котором предварительная проверка в Orders проходит, а Products отказывает в резерве. Проверка проходит через настоящий TCP/RPC и HTTP Gateway. Предсказуемость сценария не зависит от удачного порядка двух параллельных запросов.
- [x] Клиент получает документированный HTTP 400 за нехватку остатка. До исправления этот сценарий возвращал HTTP 500. После преобразования ошибки резерва в Orders тот же E2E-тест подтвердил HTTP 400 и сообщение Products о нехватке товара.

### 05. Восстановление после прерванного заказа

- [x] На реальных БД Products и Orders подготовить состоявшийся резерв, незавершённую операцию и отсутствие сохранённого заказа. Новый экземпляр обработчика восстанавливает остаток и закрывает операцию.
- [x] Вызвать обработчик повторно без ожидания тика планировщика. Остаток и журнал подтверждают один возврат. Если Products временно недоступен, незавершённую работу можно продолжить после восстановления связи.

### 06. Миграции на пустой и заполненной базе

- [x] Полная цепочка штатных миграций каждого SQL-сервиса применяется к пустой временной БД с отключённым `synchronize`.
- [x] Для миграции Orders, создающей `order_operations`, поднять предыдущую схему, записать отменённый и активный заказы и обновить базу. Оба заказа сохранились, операция `release` появилась только у отменённого. Для других миграций, преобразующих данные, проверить исходные записи и результат тем же способом.

### 07. Потерянный ответ PayPal

- [x] На границе PayPal воспроизвести таймаут и потерю ответа после принятого запроса. На PostgreSQL проверить сохранение незавершённой операции и корректное завершение после повтора новым экземпляром обработчика. Повтор использует тот же ключ идемпотентности для одной операции.
- [x] Детерминированная проверка запускается на каждом PR. Отдельная проверка адаптера обращается к PayPal Sandbox. В инструкции к выпуску платёжных изменений указан ручной путь с подтверждением покупателя и ожидаемыми результатами capture и возврата. Отчёт различает выполненную sandbox-проверку и пропуск из-за отсутствия доступа.

Локальные сценарии прошли. Проверка с Sandbox отмечена как пропущенная до предоставления реквизитов.

### 08. Параллельные записи корзины

- [x] Через общий integration-запуск поднять MongoDB версии проекта. Два конкурентных добавления разных товаров в пустую корзину одного пользователя сохраняют обе позиции. Результат прочитан из сохранённой корзины.

### 09. Конкурентное обновление сессии

- [x] На временной PostgreSQL два параллельных вызова refresh с одним токеном дают одного победителя. Проигравший получает отказ авторизации. Новый токен продолжает сессию, прежний отклоняется.

### 10. Чтение остатка после инвалидирования Redis

- [x] Поднять Redis и PostgreSQL. Прочитать товар через сервис и убедиться, что запись действительно попала в Redis. Изменить остаток штатной операцией и повторно прочитать через сервис. Значение совпадает с сохранённым остатком. Тихое переключение на in-memory должно обнаруживаться тестом.

### 11. Kafka → SSE и завершение сессии

- [x] Через публичный API открыть два потока из разных сессий владельца и поток другого пользователя. Дождаться `ready` в каждом, изменить корзину владельца и проверить получение `cart.updated` обоими его подключениями. Проверить отсутствие чужого уведомления у второго пользователя и подтвердить работоспособность его потока собственным событием.
- [x] После logout завершается поток именно этой сессии. Следующее обновление приходит во вторую сессию владельца. Ожидания ограничены по времени, падение показывает, какой поток и событие ожидались.

### 12. HTTP-контракты и Bruno

- [x] Перечислить уникальные гарантии Gateway из публичных контрактов и Bruno. Варианты входных данных собрать в таблицы unit-тестов схем. На HTTP-границе проверить фактический статус и форму ошибки.
- [x] Для защищённых маршрутов проверить назначение guard реальными запросами, включая доступ по роли и доступ владельца там, где они требуются. Снятие guard с проверяемого маршрута должно ломать тест. Сохранить коллекции Bruno для ручной работы и связать перенесённые гарантии с автоматическими проверками.

Сопоставление Bruno, контрактов и тестов приведено в [карте HTTP-контрактов Gateway](gateway-contract-tests.md).

### 13–15. Завершение покрытия по областям

Каждая строка — отдельная задача. Для каждой проверить **все** исходники своей области, включая неимпортированные файлы. Прикладные ветки получить через наблюдаемый результат, для инфраструктурного исключения указать конкретный проверяющий сценарий. Выполненная задача убирает свою область из списка отложенного покрытия.

| № | Область | Критерий приёмки |
| --- | --- | --- |
| 13 | Orders и Products | Все четыре метрики равны 100% для прикладной логики заказов, платежей, резерва и каталога, включая решения в CQRS-обработчиках. |
| 14 | Cart, Auth и Users | Все четыре метрики равны 100% для правил корзины, сессий и пользователей. Для доступа к БД и других инфраструктурных исключений установлено, какая проверка поймает поломку. |
| 15 | Gateway и `libs` | Все четыре метрики равны 100% для прикладного поведения Gateway и общих библиотек, включая схемы, guards, фильтры и исполняемые правила конфигурации. Сценарии задачи 12 используются повторно там, где уже доказывают нужное поведение. |

Задача 13 выполнена. Прикладные исходники Orders и Products входят в обязательный отчёт, а для инфраструктурных файлов указаны [проверки миграций, модулей и хранения](unit-coverage-infrastructure.md).

Задача 14 выполнена. Cart, Auth и Users выведены из списка отложенного покрытия. Проверки конкурентных записей корзины запускаются на временной MongoDB.

Задача 15 выполнена. Gateway и общие библиотеки входят в обязательный отчёт, список отложенного покрытия пуст. Выдача OpenAPI и внедрение Redis-кэша сопоставлены с проверками собранных приложений.

### 16. Итоговая приёмка и очистка

- [ ] Из чистого checkout выполнить четыре команды. Полный unit-набор работает без Docker. Все integration- и E2E-проверки обязательного набора выполняются с временными зависимостями локально и в CI.
- [ ] В списке отложенного покрытия нет файлов. Отчёт охватывает всю прикладную логику, для каждого инфраструктурного исключения указан работающий тест. Удалить только те дубли и старые вспомогательные средства, полезные проверки которых перенесены или больше не имеют вызывающего кода.
- [ ] Проверить на PR, что падение любого обязательного набора блокирует слияние и публикацию, автоматический повтор не скрывает первое падение, а логи доступны и после очистки окружения.
- [ ] Сопоставить замеры unit-прогона после переноса первого сервиса, самого тяжёлого набора и всего проекта с исходным ориентиром 30 секунд на стандартном CI runner после установки зависимостей. Зафиксировать фактическое время, отдельно указав стоимость сбора покрытия.
