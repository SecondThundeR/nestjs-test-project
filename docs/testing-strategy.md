# Стратегия тестирования

## Согласованные решения

- Unit-тесты запускаются на Node.js без Docker. Для прикладной логики действуют четыре порога покрытия по 100%. Граница и требования к исключениям описаны в [ADR-0001](adr/0001-unit-coverage-scope.md).
- Допустим точечный рефакторинг production-кода с сохранением публичных контрактов и поведения. Например, решение о допустимости отмены можно вынести из транзакции и проверить таблицей переходов. Саму транзакцию проверяем на PostgreSQL.
- Локально и в CI интеграционные тесты поднимают необходимые зависимости через Testcontainers. E2E запускает собранные приложения и инфраструктуру в изолированном Compose-проекте. Ошибка запуска обязательной зависимости завершает прогон ошибкой.
- На каждом PR проверяем реакцию платёжного кода на таймаут, потерянный ответ и повтор операции. Сбой задаём на границе PayPal, сохранение и восстановление операции проверяем на PostgreSQL. Совместимость адаптера отдельно проверяем в PayPal Sandbox. Полный путь с подтверждением покупателя проходим вручную перед выпуском изменений платёжного потока.

## Первый этап

| Уровень | Критерий приёмки |
| --- | --- |
| Unit | Проверены правила отмены заказа. Для перенесённой прикладной логики достигнуты все четыре порога покрытия. |
| Integration | При двух конкурентных попытках зарезервировать последнюю единицу товара на реальной PostgreSQL резерв получает ровно один заказ, остаток равен нулю. Отдельная проверка через HTTP и RPC подтверждает, что отказ резерва из-за нехватки остатка доходит до клиента как документированный HTTP 400. |
| E2E | Покупатель оформляет заказ на единственную единицу товара и читает через Gateway остаток 0. Два последовательных запроса отмены возвращают HTTP 200, тот же ID заказа и статус `CANCELLED`. После каждой отмены каталог показывает остаток 1. Чтение заказа от имени владельца подтверждает сохранённый статус. |

## Переход и требования к PR

- Включаем в обязательную область unit-покрытия все файлы с новой прикладной логикой и все перенесённые файлы, даже если тесты их ещё не импортируют. При переносе область расширяется. При небольшом исправлении в старом сервисе добавляем тест изменённого поведения. Конечная цель — охватить всю прикладную логику проекта.
- Существующие проверки можно удалять по мере замены их полезных сценариев.
- Слияние PR требует успешного полного unit-прогона с проверкой покрытия, всех перенесённых integration-тестов и короткого E2E-набора. Пропуск обязательного сценария из-за отсутствующей зависимости и автоматический повтор после падения не дают основания считать проверку пройденной. Логи первого падения сохраняем.
- Начальный ориентир для полного `test:unit` — 30 секунд на стандартном CI runner после установки зависимостей. Время `test:unit:cov` измеряем отдельно. Пересматриваем ориентир после переноса первого сервиса и самого тяжёлого набора. До замеров это ориентир без блокировки PR.

## Обязательные сценарии после первого этапа

| Риск | Уровень и критерий приёмки |
| --- | --- |
| Сбой между резервом в Products и сохранением заказа в Orders | Integration. Подготовить в PostgreSQL состояние после частичного сбоя. Новый экземпляр обработчика восстанавливает остаток и закрывает незавершённую операцию. Повторный запуск сохраняет тот же остаток. Обработчик вызываем напрямую, без ожидания планировщика. |
| Ошибка миграции на существующих данных | Integration. Применяем штатные SQL-миграции к пустой БД. Для миграции, преобразующей данные, дополнительно готовим записи на предыдущей версии схемы и проверяем результат обновления. Для миграции Orders с таблицей `order_operations` операция `release` должна появиться у ранее отменённого заказа, а у активного список операций должен остаться пустым. |
| Потеря изменений корзины | Integration с MongoDB. Два параллельных добавления разных товаров в пустую корзину одного покупателя сохраняют оба товара. Проверяем итог чтением сохранённой корзины. |
| Повторное использование refresh-токена | Integration с PostgreSQL. Ровно одна из двух попыток обновить сессию одним токеном успешна. Выданный refresh-токен позволяет продолжить сессию, прежний отклоняется. |
| Устаревший остаток в кэше | Integration с Redis. Прочитать товар, чтобы заполнить кэш, изменить остаток и проверить, что следующее чтение через сервис возвращает актуальное значение. |
| Адресация событий и завершение сессии | E2E с Gateway и Kafka. Открыть два подключения владельца из разных сессий и подключение другого пользователя. После готовности потоков изменить корзину. Оба подключения владельца получают `cart.updated`; чужой поток остаётся без этого уведомления. После logout поток завершённой сессии закрывается, а во вторую сессию приходит следующее обновление. |

Для отрицательной SSE-проверки нужен наблюдаемый признак работоспособности чужого потока. Например, отдельное действие второго пользователя должно доставить ему ожидаемое событие. Ожидания событий ограничиваем по времени.

## Bruno и повторяющиеся проверки

Сохраняем коллекции Bruno для ручной проверки API. В обязательный CI переносим уникальные гарантии. Варианты невалидной цены проверяем таблицей на уровне схемы и одним HTTP-примером проверяем формат ошибки. Назначение прав на конкретный маршрут проверяем запросом через Gateway, где ошибку подключения guard можно наблюдать снаружи.

## Порядок внедрения

Зависимости между задачами и критерии их приёмки приведены в [плане работ](testing-backlog.md).

1. Ввести команды `test:unit`, `test:unit:cov`, `test:integration` и `test:e2e` вместе с первым сценарием резерва и отмены. Добиться, чтобы из чистого checkout при установленных зависимостях и доступном Docker все три уровня запускались локально и в CI. Экземпляры БД, сети, порты и тома тестов изолировать от dev-окружения и параллельных прогонов. Сохранять логи до удаления временного окружения, включая случай падения проверки.
2. Добавить проверки восстановления Orders и обновления заполненной базы. Проверить обработку сбоев на границе PayPal и сохранение операций. Миграции запускать с отключённой автосинхронизацией схемы.
3. Перенести проверки корзины, сессий, кэша и доставки уведомлений. Для каждого риска использовать самый узкий уровень, на котором проявится ошибка. При переносе HTTP-сценариев сверяться с коллекциями Bruno и контрактами Gateway.
4. Пройти оставшиеся приложения и библиотеки, включить всю прикладную логику в отчёт покрытия. Для каждого исключения указать проверяющий его integration- или E2E-тест. Сверить итоговые замеры unit-прогона с ориентиром и удалить дубли, для которых уже есть эквивалентная проверка.
