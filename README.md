# Каталог продуктов с использованием микросервисов на NestJS

Система управления каталогом продуктов, корзиной и заказами, построенная на микросервисной
архитектуре с использованием NestJS + PostgreSQL + Redis + Kafka

## Стек

- **NestJS** (монорепозиторий, `apps/*` + общие `libs/*`)
- **PostgreSQL** + **TypeORM** (отдельная БД на каждый сервис, миграции для прода)
- **Redis** для кэширования (через `cache-manager`/`keyv`, с фолбэком на in-memory)
- **Kafka** (KRaft) как шина событий + паттерн **CQRS** (`@nestjs/cqrs`) в `orders`
- **JWT** + серверные сессии с ротацией refresh-токенов
- **PayPal** (sandbox) для обработки платежей
- **Winston** для логирования
- **Zod** + NestJS Standard Schema для валидации, сериализации и Code First OpenAPI
- **Vitest** для unit и e2e тестов, **oxlint** + Prettier для качества кода
- **Rspack** для параллельной сборки монорепозитория
- **Docker** / **docker-compose** для контейнеризации

## Архитектура

Наружу торчит единственная точка входа - **API Gateway** (REST). Между собой сервисы общаются
по **TCP** (request/response) и через **Kafka** (события). У каждого прикладного сервиса - своя
БД PostgreSQL

| Сервис     | Порт (dev) | БД (порт)       | Назначение                                              |
| ---------- | ---------- | --------------- | ------------------------------------------------------- |
| `gateway`  | 3000       | -               | REST API, JWT-guard'ы, Swagger, маршрутизация в сервисы |
| `products` | 3001       | products (5532) | CRUD продуктов, кэш в Redis, **Code First** OpenAPI     |
| `cart`     | 3002       | cart (5533)     | Корзина (TypeORM `EntitySchema`), потребитель Kafka     |
| `orders`   | 3003       | orders (5534)   | Заказы, оплата PayPal, CQRS, **Schema First** OpenAPI   |
| `users`    | 3004       | users (5535)    | Хранилище пользователей (внутренний сервис)             |
| `auth`     | 3005       | auth (5536)     | JWT + сессии, регистрация/логин/refresh/logout          |

Инфраструктура: **Redis** (6380), **Kafka** (9094 снаружи / 9092 внутри сети)

### Code First / Schema First

- **Code First** (`products`) - OpenAPI генерируется из общих Zod-схем через `@nestjs/swagger`.
  Документация: `GET /api/docs/products`
- **Schema First** (`orders`) - сервис реализован под вручную написанный контракт
  `apps/gateway/src/orders/orders.openapi.yaml`, соответствие проверяется контракт-тестом
  (`orders.contract.e2e-spec.ts`). Документация: `GET /api/docs/orders`

### Авторизация

JWT содержит `sid` (id сессии). На каждый защищённый запрос gateway дергает `auth.verify`, поэтому
`logout` мгновенно инвалидирует access-токен. Refresh-токены хранятся хешированными, ротируются и
имеют скользящий срок жизни (`REFRESH_TTL_DAYS`). Мёртвые сессии подчищает ежедневный cron

Миграция засевает администратора по умолчанию:

- **email:** `admin@example.com`
- **password:** `admin12345`

## Запуск

### Через Docker (рекомендуется)

```bash
cp .env.example .env      # задайте JWT_SECRET (openssl rand --hex 64)
pnpm run docker:up        # поднимет все сервисы, БД, Redis и Kafka
```

В контейнерах используется `DB_SYNCHRONIZE=false` + автозапуск миграций (`DB_MIGRATIONS_RUN=true`)

### Локально (dev)

```bash
corepack enable
pnpm install
pnpm run docker:db        # только инфраструктура (БД + Redis + Kafka)
pnpm run start:dev        # все сервисы через concurrently (synchronize=true)
```

После запуска:

- REST API: `http://localhost:3000/api`
- Code First docs: `http://localhost:3000/api/docs/products`
- Schema First docs: `http://localhost:3000/api/docs/orders`
- Healthcheck: `http://localhost:3000/api/health`

## Основные эндпоинты

| Метод/путь                                                     | Доступ                            | Описание             |
| -------------------------------------------------------------- | --------------------------------- | -------------------- |
| `POST /api/auth/register` \| `login` \| `refresh`              | публично                          | получение токенов    |
| `POST /api/auth/logout`                                        | JWT                               | завершение сессии    |
| `GET/POST/PATCH/DELETE /api/product`                           | чтение - публично, запись - admin | CRUD продуктов       |
| `GET/POST/PATCH/DELETE /api/cart`                              | JWT                               | управление корзиной  |
| `POST/GET /api/orders`, `.../pay`, `.../capture`, `.../cancel` | JWT                               | заказы и оплата      |
| `PATCH /api/orders/:id/status`                                 | admin                             | смена статуса заказа |

## Миграции

Для каждого сервиса - свой `data-source.ts` и набор миграций. В проде `synchronize` выключен

```bash
pnpm run migration:run:all       # применить миграции всех сервисов
pnpm run migration:run:products  # либо по одному сервису
```

## Тесты

```bash
pnpm test           # unit-тесты (Vitest)
pnpm run test:e2e   # e2e и контракт-тесты
pnpm run test:cov   # unit-тесты с покрытием
pnpm run lint       # type-aware oxlint + проверка Prettier
pnpm run typecheck  # TypeScript 6 без генерации файлов
```

Внешние зависимости (PayPal, Redis) в тестах замоканы, поэтому реальная инфраструктура не нужна

## Переменные окружения

Все переменные и их дефолты - в [`.env.example`](./.env.example). Ключевые моменты:

- `JWT_SECRET` - обязателен
- `REDIS_HOST` - оставьте пустым, чтобы использовать in-memory кэш вместо Redis
- **PayPal опционален:** без `PAYPAL_CLIENT_ID` / `PAYPAL_CLIENT_SECRET` платёжные эндпоинты
  вернут ошибку, всё остальное работает. Ключи берутся из
  [PayPal sandbox](https://developer.paypal.com/dashboard/applications/sandbox)

## Исходное задание

### Описание

Необходимо разработать систему для управления каталогом продуктов, которая будет состоять из нескольких микросервисов с использованием Nest.js и базой данных PostgreSQL. Каждый микросервис будет отвечать за определенные функциональности.

### Используемые технологии

- Nest.js для разработки микросервисов.
- База данных PostgreSQL.
- TypeORM - библиотека, предназначенная для работы с базами данных через объектно-реляционное отображение.
- Логирование событий с использованием библиотеки Winston.
- Обработки платежей с использованием PayPal.
- Docker для контейнеризации.
- Jest для модульного тестирования.

### Требования

1. Разделение системы на следующие микросервисы:
   - Каталог продуктов отвечает за управление продуктами, их создание, просмотр, обновление и удаление.
   - Корзина покупок отвечает за управление корзиной покупок пользователей.
   - Заказы отвечают за управление заказами пользователей.
2. REST API для взаимодействия между микросервисами и клиентским приложением.
3. Один из сервисов написать с использованием подхода "Code First" (генерация OpenAPI исходя из написанного кода).
4. Один из сервисов написать с использованием подхода "Schema First" (реализация сервиса под контракт OpenAPI, написанный вручную).
5. Авторизация и аутентификация
   - Использование JSON Web Tokens (JWT) для аутентификации пользователей.
   - Механизм сессий для управления состоянием аутентифицированных пользователей.
   - Проверка валидности токена перед выполнением запросов.
6. Механизм кэширования запросов и данных для повышения производительности.

### Дополнительно

1. Для typeorm настроить миграции схем для продакшн сборки (для разработки можно использовать synchronize: true, чтобы не терять время)
2. Настроить микросервисную архитектуру с использованием kafka и паттерна cqrs
   - Kafka можно запустить локально с использованием docker и docker-compose
   - Настроить базу данных redis для одного из микросервисов

### Так же проект предполагает

- Качество и чистоту кода микросервисов.
- Соответствие требованиям и функциональности, указанным в задании.
- Корректность обработки ошибок и возврата соответствующих статусов.
- Качество и полнота тестового покрытия микросервисов.
- Применение правил валидации данных и обработки ввода пользователя.
- Качество логирования.
