# Каталог продуктов с использованием микросервисов на NestJS

Система управления каталогом продуктов, корзиной и заказами, построенная на микросервисной
архитектуре с использованием NestJS + PostgreSQL + MongoDB + Redis + Kafka

## Стек

- **NestJS** (монорепозиторий, `apps/*` + общие `libs/*`)
- **PostgreSQL** + **TypeORM** (products, orders, users, auth; миграции для прода)
- **MongoDB** + **TypeORM MongoRepository** (документы корзин в cart)
- **Redis** для кэширования (через `cache-manager`/`keyv`, с фолбэком на in-memory)
- **Kafka** (KRaft) как шина событий + паттерн **CQRS** (`@nestjs/cqrs`) в `orders`
- **JWT** + серверные сессии с ротацией refresh-токенов
- **PayPal** (sandbox) для обработки платежей
- **Winston** для логирования
- **Zod** + NestJS Standard Schema для валидации, сериализации и Code First OpenAPI
- **Vitest** для unit и e2e тестов, **oxlint** + Prettier для качества кода
- **Rspack** для параллельной сборки монорепозитория
- **Docker** / **docker-compose** для контейнеризации

## Архитектура

Наружу торчит единственная точка входа - **API Gateway** (REST). Между собой сервисы общаются
по **TCP** (request/response) и через **Kafka** (события). У каждого прикладного сервиса - своя
БД: PostgreSQL, а у cart — MongoDB

| Сервис     | Порт (dev) | БД (порт)       | Назначение                                              |
| ---------- | ---------- | --------------- | ------------------------------------------------------- |
| `gateway`  | 3000       | -               | REST API, JWT-guard'ы, Swagger, маршрутизация в сервисы |
| `products` | 3001       | products (5532) | CRUD продуктов, кэш в Redis, **Code First** OpenAPI     |
| `cart`     | 3002       | MongoDB (27017) | Корзина (TypeORM + MongoDB), потребитель Kafka          |
| `orders`   | 3003       | orders (5534)   | Заказы, оплата PayPal, CQRS, **Schema First** OpenAPI   |
| `users`    | 3004       | users (5535)    | Хранилище пользователей (внутренний сервис)             |
| `auth`     | 3005       | auth (5536)     | JWT + сессии, регистрация/логин/refresh/logout          |

Инфраструктура: **Redis** (6380), **Kafka** (9094 снаружи / 9092 внутри сети)

### Code First / Schema First

- **Code First** (`products`) - OpenAPI генерируется из общих Zod-схем через `@nestjs/swagger`.
  Документация: `GET /api/docs/products`
- **Schema First** (`orders`) - сервис реализован под вручную написанный контракт
  `apps/gateway/src/orders/orders.openapi.yaml`, соответствие проверяется контракт-тестом
  (`orders.contract.integration-spec.ts`). Документация: `GET /api/docs/orders`

### Авторизация

Gateway проверяет JWT через Passport (`passport-jwt` и `@nestjs/passport`).
JWT содержит `sid` (id сессии). На каждый защищённый запрос gateway дергает `auth.verify`, поэтому
`logout` мгновенно инвалидирует access-токен. Refresh-токены хранятся хешированными, ротируются и
имеют скользящий срок жизни (`REFRESH_TTL_DAYS`). Мёртвые сессии подчищает ежедневный cron

Администратор автоматически не создаётся. После применения миграций задайте
`ADMIN_EMAIL`, `ADMIN_NAME` и `ADMIN_PASSWORD` через окружение и выполните:

```bash
pnpm run admin:create
```

Пароль должен содержать минимум 12 символов. Для хеширования используется Argon2id. Не передавайте пароль аргументом команды и не сохраняйте
его в репозитории. Команда создаёт только нового пользователя: занятый email
приводит к ошибке, права и пароль существующих пользователей не меняются.
Подключение задаётся переменными `USERS_DB_*` из `.env`; миграции и synchronize
эта команда не запускает. Для Docker можно выполнить собранную команду внутри
контейнера users, передав переменные окружения:

```bash
docker compose exec -e ADMIN_EMAIL -e ADMIN_NAME -e ADMIN_PASSWORD users node dist/typeorm/apps/users/src/scripts/create-admin.cli.js
```

Миграция `RemoveDefaultAdmin` удаляет ранее созданного стандартного администратора
только при совпадении исходных ID, email и хеша пароля. Изменённые учётные записи
не затрагиваются; откат миграции не восстанавливает известные credentials.
При обновлении существующего окружения очистите кеш users/auth либо дождитесь
его TTL (по умолчанию 30 секунд), чтобы старые сессии перестали проходить проверку.

## Запуск

### Через Docker (рекомендуется)

```bash
cp .env.example .env      # задайте JWT_SECRET (openssl rand --hex 64)
pnpm run docker:up        # поднимет все сервисы, БД, Redis и Kafka
```

В контейнерах используется `DB_SYNCHRONIZE=false` + автозапуск миграций (`DB_MIGRATIONS_RUN=true`)

### Локально (dev)

```bash
cp .env.example .env      # для первого запуска; задайте JWT_SECRET
corepack enable
pnpm install
pnpm run docker:db        # только инфраструктура (БД + Redis + Kafka)
pnpm run start:dev        # все сервисы через concurrently (synchronize=true)
```

После запуска:

- REST API: `http://localhost:3000/api/v1`
- Code First docs: `http://localhost:3000/api/docs/products`
- Schema First docs: `http://localhost:3000/api/docs/orders`
- Healthcheck: `http://localhost:3000/api/v1/health`

## Миграции

Для SQL-сервисов — свой `data-source.ts` и набор миграций. Cart использует MongoDB и не запускает TypeORM-миграции. В проде `synchronize` выключен

```bash
pnpm run migration:run:all       # применить миграции всех сервисов
pnpm run migration:run:products  # либо по одному сервису
```

`pnpm run test:integration migrations` проверяет чистую установку схем Auth, Orders, Products и Users и обновление баз с существующими заказами и пользователями. Для каждого сценария создаётся отдельная БД во временном контейнере PostgreSQL.

## Тесты

```bash
pnpm run test:unit        # быстрые unit-тесты без сервисов и Docker
pnpm run test:unit:cov    # те же тесты с отчётом покрытия
pnpm run test:integration # интеграционные тесты с временными PostgreSQL, MongoDB и Redis (нужен Docker)
pnpm test                 # существующий набор проверок (Vitest)
pnpm run test:e2e         # заказ, повторная отмена и доставка SSE через Gateway в отдельном Compose-проекте
pnpm run lint             # type-aware oxlint
pnpm run format:check     # проверка Prettier
pnpm run typecheck        # TypeScript 6 без генерации файлов
```

Быстрые тесты называются `*.unit.spec.ts`. Новые исходники приложений и библиотек входят в unit-отчёт автоматически. Границы отчёта заданы в [конфигурации Vitest](vitest.config.ts).

В интеграционный набор входят проверки TCP-сервисов и HTTP-контрактов с локальными подменами соседних сервисов. Тесты хранения и конкуренции используют временные базы и Redis.

Для `test:e2e` нужны Bash и локальный Docker с Compose 2.24.4 или новее. Команда собирает образ из текущего checkout, запускает шесть приложений и инфраструктуру, дожидается готовности и создаёт администратора штатной CLI. Используются тестовые настройки из `test/e2e/compose.env`. Gateway и тестовая БД Products доступны на динамических портах loopback. В сценарии отказа резерва тест удерживает блокировку товара до момента, когда Products попытается его списать, и проверяет HTTP 400 через Gateway. Каждый прогон получает собственную сеть и тома; после завершения они удаляются вместе с контейнерами и тегом образа. При ошибке вывод запуска, состояния контейнеров и логи сервисов остаются в `test-results/e2e/<имя-проекта>/`.

## Исходное задание

### Описание

Необходимо разработать систему для управления каталогом продуктов, которая будет состоять из нескольких микросервисов с использованием Nest.js и базой данных PostgreSQL. Каждый микросервис будет отвечать за определенные функциональности.

### Используемые технологии

- Nest.js для разработки микросервисов.
- База данных PostgreSQL.
- TypeORM - библиотека, предназначенная для работы с базами данных через объектно-реляционное отображение.
- Логирование событий с использованием библиотеки Winston.
- Обработки платежей с использованием PayPal.
- Docker для контейнеризации.
- Jest для модульного тестирования.

### Требования

1. Разделение системы на следующие микросервисы:
   - Каталог продуктов отвечает за управление продуктами, их создание, просмотр, обновление и удаление.
   - Корзина покупок отвечает за управление корзиной покупок пользователей.
   - Заказы отвечают за управление заказами пользователей.
2. REST API для взаимодействия между микросервисами и клиентским приложением.
3. Один из сервисов написать с использованием подхода "Code First" (генерация OpenAPI исходя из написанного кода).
4. Один из сервисов написать с использованием подхода "Schema First" (реализация сервиса под контракт OpenAPI, написанный вручную).
5. Авторизация и аутентификация
   - Использование JSON Web Tokens (JWT) для аутентификации пользователей.
   - Механизм сессий для управления состоянием аутентифицированных пользователей.
   - Проверка валидности токена перед выполнением запросов.
6. Механизм кэширования запросов и данных для повышения производительности.

### Дополнительно

1. Для typeorm настроить миграции схем для продакшн сборки (для разработки можно использовать synchronize: true, чтобы не терять время)
2. Настроить микросервисную архитектуру с использованием kafka и паттерна cqrs
   - Kafka можно запустить локально с использованием docker и docker-compose
   - Настроить базу данных redis для одного из микросервисов

### Так же проект предполагает

- Качество и чистоту кода микросервисов.
- Соответствие требованиям и функциональности, указанным в задании.
- Корректность обработки ошибок и возврата соответствующих статусов.
- Качество и полнота тестового покрытия микросервисов.
- Применение правил валидации данных и обработки ввода пользователя.
- Качество логирования.

## SSE: уведомления о заказах и корзине

`GET /api/v1/events` открывает поток `text/event-stream` с заголовком
`Authorization: Bearer <accessToken>`. Используйте streaming `fetch`: нативный
`EventSource` не поддерживает этот заголовок.

| Событие                                                                  | JSON data              | Действие клиента                        |
| ------------------------------------------------------------------------ | ---------------------- | --------------------------------------- |
| `ready`                                                                  | `{}`                   | Загрузить заказы и корзину через REST   |
| `order.created`, `order.paid`, `order.cancelled`, `order.status-changed` | `{ "orderId": "..." }` | Перезагрузить заказ                     |
| `cart.updated`                                                           | `{}`                   | Перезагрузить корзину                   |
| `heartbeat`                                                              | `{}`                   | Поддержание соединения каждые 15 секунд |

Gateway получает события Kafka и отправляет их только владельцу, во все его
подключения. `cart.updated` публикуется после сохранения, включая асинхронную
очистку корзины по `order.created`. Все изменения выполняются существующими REST
запросами. Оплата уведомляется после capture, в том числе через PayPal return.

Сессия проверяется перед отправкой уведомлений и каждые 15 секунд (таймаут 5 секунд).
Успешный logout через gateway немедленно закрывает все SSE-соединения этой сессии;
соединения других сессий пользователя остаются открытыми. Периодические проверки
сохраняются для отзыва сессии вне этого gateway. Соединение также закрывается при
истечении access-токена или ошибке проверки.
После 401/403 клиент должен обновить токен или выполнить login. После переподключения
и получения `ready` клиент должен повторно загрузить данные через REST.

`pnpm run test:e2e cart-events` проверяет доставку `cart.updated` через Kafka в два SSE-потока владельца и завершение одного потока после logout. Тест открывает третий поток от имени другого покупателя и подтверждает, что тот получает только обновление своей корзины.

Этот же E2E-набор проверяет доставку событий заказов из Kafka в SSE и передачу ID заказа в уведомлении.

### Резервирование остатков

Orders резервирует все позиции заказа одной транзакцией в Products. SQL-проверка
остатка предотвращает перепродажу при параллельных запросах. Резерв и возврат
идемпотентны по ID заказа; журнал хранится в `stock_reservations`. При ошибке
создания заказа выполняется компенсация, а повторная отмена повторяет возврат
без двойного увеличения остатков. Отмена старых заказов без записи в журнале
также поддерживается. Примените миграции Products перед обновлением Orders.

Перед резервированием Orders записывает операцию в `stock_intents`. Сохранение
заказа и удаление этой записи выполняются в одной транзакции. Каждые 30 секунд
фоновая задача обрабатывает до 100 незавершённых операций: возвращает резерв,
если заказ не был сохранён, и повторяет попытку при недоступности Products.
Блокировка строки защищает активное создание заказа и несколько экземпляров
Orders от конкурентной очистки. RPC резервирования и возврата имеют таймаут 5 секунд.

Перед обновлением Orders примените `pnpm migration:run:orders`. Восстановление
работает для операций, начатых после этого обновления; старые резервы без записи
в `stock_intents` по-прежнему требуют ручной сверки. Платёжные операции и повторная
доставка событий Kafka этим механизмом не обрабатываются.

Для проверки транзакций и конкурентных резервов Products выполните:

```bash
pnpm run test:integration
```

Testcontainers запускает отдельную PostgreSQL на свободном порту, применяет миграции Products и удаляет контейнер после прогона. При первом запуске Docker потребуется скачать образы. Логи PostgreSQL записываются во время работы в `test-results/integration/`. При сбое CI сохраняет их вместе с выводом Vitest.

`pnpm run test:integration stock-cache` проверяет, что резерв удаляет запись об остатке из временного Redis, а следующее чтение Products заново кэширует значение из PostgreSQL.

Тот же integration-прогон проверяет восстановление резервов Orders. Для него запускаются отдельные временные БД Orders и Products со штатными миграциями. Запуск только этого набора:

```bash
pnpm run test:integration stock-recovery
```

## MongoDB: корзина

Подключением MongoDB управляет `TypeOrmModule`, операции выполняет `MongoRepository`.
Пакет `mongodb` используется как драйвер TypeORM.
Cart хранит корзину одним документом в коллекции `carts`. `_id` равен `userId`,
поэтому на пользователя существует одна корзина. Внутренняя версия документа
защищает от потери изменений при параллельных запросах, включая несколько экземпляров
сервиса. При конфликте операция повторяется с актуальным состоянием и повторной
проверкой остатка; после 64 конфликтов возвращается 409, запрос можно повторить.
Kafka-событие `cart.updated` публикуется после успешной записи.

`pnpm run test:integration cart-concurrency` проверяет одновременное добавление двух товаров в пустую корзину. Два экземпляра CartService используют отдельные подключения к одному временному MongoDB версии из Compose. Проверка читает обе позиции из сохранённого документа.

Локальное подключение: `CART_MONGODB_URI=mongodb://127.0.0.1:27017/cart`.
В Docker сервис использует `cart-mongodb:27017`, данные сохраняются в отдельном volume.
Для внешнего MongoDB URI должен содержать имя базы и при необходимости учётные данные.
Переменные `DB_SYNCHRONIZE` и `DB_MIGRATIONS_RUN` относятся только к SQL-сервисам.
