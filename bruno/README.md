# Проверка API в Bruno

Три независимые коллекции:

| Каталог | Назначение |
| --- | --- |
| `bruno` | 180 последовательных запросов, без зависимости от PayPal |
| `bruno-sse` | Существующий ручной сценарий SSE, 13 запросов |
| `bruno-paypal` | 21 ручной запрос оплаты, доставки и возврата |

## Запуск

1. Из корня проекта запустите `pnpm docker:up`. Дождитесь готовности сервисов и миграций.
2. Создайте отдельного тестового администратора по [инструкции проекта](../README.md#авторизация): задайте `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD` и выполните `pnpm admin:create` из корня проекта. Для Docker используйте команду из той же инструкции. Администратор по умолчанию больше не создаётся.
3. Скопируйте `environments/Local.bru` в `environments/Private.bru`. В копии заполните `email` и `password` реквизитами созданного администратора; при необходимости измените `baseUrl`. `Private.bru` исключён из Git, а `Local.bru` служит шаблоном без реквизитов.
4. В Bruno откройте каталог `bruno` через Open Collection и выберите окружение **Private**.
5. Запустите всю коллекцию последовательно через Collection Runner. Параллельный запуск не поддерживается: запросы передают ID и токены друг другу.

Через [Bruno CLI](https://github.com/usebruno/bruno/blob/main/packages/bruno-cli/readme.md):

```sh
cd bruno
npx @usebruno/cli run --env Private
```

Базовый URL содержит `/api/v1`. Реквизиты администратора храните только в исключённом из Git окружении `Private`. ID, email и токены сохраняются через `bru.setVar` только на время выполнения. Не сохраняйте реальные пароли в Git.

## Покрытие

| Папка | Проверки |
| --- | --- |
| 01 Setup | Health, вход администратора, регистрация двух независимых пользователей |
| 02 Authentication | Повторный email, валидация регистрации и входа, запрет назначения роли, регистр email, профиль без пароля, ротация refresh и запрет повторного использования |
| 03 Access control | Все защищённые HTTP-маршруты без JWT и с повреждённым JWT; запрет административных операций обычному пользователю |
| 04 Products | Публичное чтение, CRUD, кэш после изменения, отсутствующие товары, типы и границы полей, цена с лишними десятичными знаками, нулевая цена и значения по умолчанию |
| 05 Cart | Новая и сохранённая корзина, слияние количества, суммы и округление, остатки, отсутствие товара, удаление количеством 0, удаление позиции, изоляция пользователей |
| 06 Orders | Пустая корзина, адрес, изменившиеся остатки, создание и резервирование, свои и чужие заказы, переходы статусов, capture до оплаты, отмена и её идемпотентность, возврат остатков, публичные callback-маршруты |
| 07 Cleanup | Очистка корзины, удаление товаров и проверка кэша, выход из всех созданных сессий, отказ по отозванным access/refresh |

Каждый запрос содержит тест статуса. Ошибки проверяют statusCode и message; ключевые успешные сценарии дополнительно проверяют содержимое ответа.

Коллекция создаёт уникальных пользователей, товары и заказы. Товары удаляются, заказы отменяются, сессии закрываются. Пользователи и история заказов остаются: API не предоставляет их удаления. При прерванном прогоне выполните Cleanup, пока runtime-переменные доступны. Основной набор не меняет корзину администратора.

## Результат проверки

На локальном приложении 30.10.2026: 179/180 запросов, 350/352 тестов. На двух запусках `07 Cleanup / Clear fixture cart` вернул HTTP 500 вместо 200 после сценария создания и отмены заказа. Тест сохраняет контрактное ожидание 200 и показывает эту проблему приложения.

## Ограничения

Это покрытие HTTP-маршрутов и основных ветвей бизнес-логики, а не всех возможных комбинаций входных данных. SSE проверяется отдельно вручную. Успешные PayPal/capture/refund и доставка требуют sandbox и подтверждения покупателем. Истечение JWT/refresh по времени, сбои инфраструктуры, конкурирующие переходы с HTTP 409 и ошибки внешнего PayPal требуют отдельного управляемого окружения или fault injection; обычный Collection Runner их достоверно не моделирует.
